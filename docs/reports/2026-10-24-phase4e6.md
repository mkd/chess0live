## Implementation

`tools/train.py` provides read-only planning, digest-bound recipes, a tiny
synthetic smoke command, and actual training/export/qualification. `run` accepts
local binpack/bin data and optional compatible parent NNUE weights with a fresh
optimizer. It records actual checkpoint steps, processed samples, source/runtime
identities, resource allowance and output lineage. Metadata schema 2 adds these
work/lineage fields; schema 1 remains readable. Unique game history is never
inferred from repeated training samples.

The external trainer is pinned to
[`aa2fff2f4a67d1a268dad991fcc03430781fde15`](https://github.com/official-stockfish/nnue-pytorch/tree/aa2fff2f4a67d1a268dad991fcc03430781fde15).
Its HalfKAv2_hm, threat/pawn-pair features, PSQT, stack dimensions and compressed
writer match SF19. Current development source had removed PSQT and later changed
serialization; merely checking the outer version would have been insufficient.
The export always passes through the independent SF19 oracle before the public
run succeeds. Upstream notices/data-format ancestry remain in the external cache;
none of its code is linked into chess0live.

`tools/training_setup.py` automatically configures an isolated Python 3.12
runtime with 21 pinned packages. First use downloaded the hash/size-pinned
standalone Python 3.12.15 and all package archives successfully; offline reuse
also passed. Runtime versions include Torch 2.14.1, NumPy 1.26.4 and Numba 0.68.0.
The initial wheel/runtime lock supports macOS 14+ ARM64 only. No system Python,
global settings, CUDA package set or Docker training image was installed.

## Real execution

All real training used one tensor thread. Admission now conservatively includes
four additional loader/prefetch threads, checks physical memory and reserves
8 GiB, with batch size capped at 1,024. The measured host has 18 logical CPUs and
64 GiB memory; daytime limits were 9 workers and 32 GiB. No daytime exception or
long training campaign was needed for these bounded correctness checks.

## Investigation record and limits

Early backend and public exploratory runs are retained under
`build/phase4e6-research/` and `results/phase4e6-20261024/smoke/`. Review found
additional native loader threads beyond the trainer's `num_workers` setting;
admission was corrected before the accepted runs. The initial system memory
query was blocked by execution permissions; it was independently verified and
then succeeded in the accepted runs. Unknown memory now refuses admission.
Upstream checks its time limit only at epoch boundaries; the public wrapper's
process-group timeout supplies the actual hard limit. A killed run is failed,
and no partial checkpoint recovery is promised. Final review found that killing
the qualification wrapper first could strand its separately grouped children.
The corrected path signals the wrapper to unwind its harness before bounded
escalation; the final parent run and real cancellation regression passed.

Evidence is in `results/phase4e6-20261024/`: both accepted run directories,
`tool-tests.log`, `cancellation-tests.log`, `independent-audit.json`, the
resource/RSS console log and
`preservation.json`. Default network/engine selection is unchanged. Pinned
Stockfish oracle source was reused from the existing cache; no new oracle
source download was needed. Training source and runtime setup had real online
first-use verification. Payloads, environments, data and checkpoints remain
outside Git.

This establishes a reproducible configuration/artifact workflow and exported
arithmetic agreement, not bit-identical cross-machine learning, dataset quality
or improved play. Native MPS/CUDA, other training hosts, held-out validation,
full optimizer resume and competitively trained defaults are unverified or
unimplemented. No match/puzzle campaign, UCI gameplay, sanitizer/race run or
foreign training execution was added to this tooling-only checkpoint.
