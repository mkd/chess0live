## Implementation and boundaries

`TT Move Hints` adds a separate full-position-key move cache to ordinary search.
When a legal contextual TT move is available, it retains priority. Otherwise a
hint is matched against the complete legal Move, including promotion and flags,
and used only to order that list. It never supplies a score, bound, cutoff or
LMR exemption. Existing draw-sensitive score keys, score-entry count/index mask,
replacement policy and `hashfull` meaning are unchanged. Changing order can
still change selective search, so this is an opt-in policy rather than a
result-preserving implementation optimization when enabled.

Each shared hint slot is 16 bytes, one per existing 64-byte score bucket, within
the 96-byte-per-bucket Hash sizing reservation. Hash 64 retains 2,097,152 score
entries (32 MiB) and adds 524,288 hints (8 MiB) only when enabled. This describes
retained table storage, not network/worker memory or transactional resize peaks.
Disabling releases hint storage when the next search applies the requested policy.
Allocation failures propagate explicitly before changing the previous tables or
policy bookkeeping; they do not silently run with a different option value.

The same striped locks protect copies of hint entries across workers; score and
hint locks never nest. Clears, resizes and policy/worker configuration changes
occur while workers are idle. Only completed ordinary positive-depth nodes
publish hints. Quiescence, null/verification/ProbCut subtrees, stopped nodes and
restricted root nodes are excluded; ordinary descendants of a restricted root
remain eligible. Direct speculative cutoffs publish no hint. Separate optional
`move-hints v1` diagnostics report enabled storage and worker-summed probes,
full-key hits, legal matches and stores; diagnostics stay absent when off.
