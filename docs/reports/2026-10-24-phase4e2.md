# Phase 4E.2: remaining target builds and runtime coverage

October 24, 2026. All six required targets now have successful build evidence.
Five have bounded execution evidence across the two Phase 4E checkpoints;
Windows ARM64 remains build-only. No engine implementation or playing default
changed, and no performance/strength or release claim follows.

## Changes and results

| Target | Compiler / route | Result in this checkpoint |
| --- | --- | --- |
| Linux RISC-V64 | Debian GCC 14.2.0; QEMU 10.0.13 in ARM64 Linux | Engine and seven tests built; 8/8 runtime checks passed; separate Syzygy suites passed |
| Windows ARM64 | LLVM-MinGW 20261020 / Clang 23.1.4 on macOS | Engine and seven tests built; PE architecture/imports inspected; runtime unverified |
| Windows x86-64 | Existing MinGW GCC 16.2.0 build; Wine 10 in emulated x86-64 Linux | 8/8 runtime checks passed; separate Syzygy suites passed |

The verifier now accepts an explicit Windows-only `--execution compatibility`
route with a mandatory runner argument array. It keeps PE architecture,
compiler configuration, network, suite completion, exit status, timeouts and
artifact-drift checks. Native/VM host checks and the emulator route are
unchanged. A Wine result cannot be presented as native Windows validation.
Thirty-four verifier unit tests and two Make recipe checks passed.

Each successful runtime set exercised board/perft, NNUE, independent update
and dense arithmetic, search, selective/time policies, and two-worker UCI
handshake/readiness/search/stop/quit. Each passed twelve pinned raw/wrapped
NNUE goldens, 537 incremental/full-refresh positions, 360 independent update
transitions, and 1,515 dense cases / 84,126 repeated output comparisons.
Both workers performed work in the UCI checks. All sixteen checks exited zero.
These are not fresh comparisons with the external 2,057-position SF19 stage
oracle, nor full sanitizer/race-suite runs.

Both new execution routes additionally passed the existing Syzygy suites:
140 exact WDL oracle cases with DTZ outcome/legality, special moves, clocks,
fallback, malformed data and concurrent probes, plus six search scenarios each
at Threads 1 and 4. The 72-file / 4,381,961-byte external test corpus was
verified against its pinned manifest; no table data was added to Git.

## Target setup and limitations

The RISC-V compiler package is `g++-14-riscv64-linux-gnu 14.2.0-19cross1`;
it accepted C++26 mode and linked without extra atomic libraries. Its
RV64GC/LP64D baseline and final ELF attributes were inspected; no vector
extension was enabled. QEMU package version is
`1:10.0.13+ds-0+deb13u1`, invoked explicitly with
`qemu-riscv64 -L /usr/riscv64-linux-gnu`. The loader prefix is not a new Make
sysroot. QEMU's host/guest memory-model limitations mean this is emulated
correctness evidence, not native hardware race-freedom or speed evidence.

The official LLVM-MinGW macOS universal archive was verified against its
published SHA-256 and size before extraction:
`e9c13e4ede38e715003ffc674d4d00a1088df8235439d1f0c16188ff0704c17e`,
124,415,944 bytes. It remains under ignored `build/toolchains/`, with upstream
notices intact. Windows ARM64 uses the normal `-std=c++2c -pthread -static`
Make settings; imports contain Windows OS/UCRT dependencies, without separate
compiler C++/unwind runtime DLL requirements observed.

Wine ARM64 did not complete prefix bootstrap. A 90-second position-test probe,
a 30-second loader diagnostic (`cmd /c ver`), and a 45-second fresh-prefix
probe with menu-builder disabled all exited via timeout before any chess-test
completion marker. Required Debian Wine dependencies were present. Preserve
the logs and label this **environment startup incomplete**, not an engine
correctness failure, native Windows test, or successful compatibility run.
Further Wine diagnosis is outside this bounded checkpoint.

Wine x86-64 package `10.0~repack-6` completed startup and the actual checks.
Its initial bootstrap emitted headless-display, missing 32-bit helper and
Rosetta diagnostics; these are retained in the preflight log. The subsequent
64-bit suites and UCI sessions completed and exited zero. This route layers
Wine compatibility over Docker x86-64 CPU emulation on ARM64. It does not
establish native Windows behavior, GUI integration, or native throughput.

GCC emitted anonymous-namespace linkage warnings in tests that deliberately
include the NNUE implementation; Clang reported Fathom's unused `numWdl`.
These warnings are recorded, not silently relabeled as warning-free builds.
No engine source change or correctness defect was identified from them.

## Next milestone and owner feedback

Phase 4E.3 will establish one-command tooling setup: automatic isolated
dependency installation for tools/tests/benchmarks, preserving user settings.
Host/target provisioning and network create/train/validate/select commands
follow on that foundation. Network history must distinguish known unique games,
positions, processed samples, training steps/epochs and checkpoint lineage;
unknown experience counts remain unknown and do not imply strength.
This accepted feedback is in [Requirements](../REQUIREMENTS.md) and the
[roadmap backlog](../ROADMAP.md#tooling-usability-backlog--accepted-october-24-2026).
It is planned functionality, not delivered training or automatic setup.

Native Windows acceptance, Windows ARM64 execution and broader platform/SDK
coverage remain explicit gaps. They do not justify repeating the same Wine
startup experiments indefinitely or blocking unrelated tooling development.
