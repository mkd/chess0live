# Phase 4E.1: portable runtime verification

October 24, 2026. The first Phase 4E checkpoint is complete. Current engine and
correctness binaries now have repeatable execution evidence for macOS ARM64,
Linux ARM64 in a VM, and Linux x86-64 under emulation. This is a portability
checkpoint, not a search change, speedup, strength result, or release.

## Change and bounded scope

- All C++ test link recipes now pass `LDLIBS`, matching the engine. Previously,
  a target-specific runtime library could link the engine but be omitted from
  its correctness executables.
- `make runtime-binaries` builds the engine and seven standalone suites without
  trying to execute a cross-compiled binary on the build host.
- `make verify-runtime` runs the checks natively. The separate Python verifier
  also accepts an explicitly declared VM or synchronous emulator route.
- The verifier independently checks executable headers/ISA and network digest,
  requires every suite to finish without skips, records commands/logs/hashes,
  checks two-worker UCI activity, and retains failure evidence. Timeouts and
  artifact drift cannot produce a passing report.

No engine, evaluation, pruning, clock, cache, or tablebase implementation changed.
The ordinary macOS release binary remains byte-identical to the Phase 4D.7
candidate. All 24 pinned engine/Fathom sources, 62 protected files, the owner's
editable batch runner, GUI bundle `0.1-dev-4b8b35d` and other snapshots, and
README introduction remained unchanged. Conservative LMR remains enabled;
ProbCut and the other experimental pruning options remain disabled.

## Executed checks

Twenty-eight verifier unit tests and two Make recipe tests passed. These cover
all six supported executable headers, wrong architecture/bitness/endian,
truncated headers, bad PE offsets, wrong network/stamp, command argument paths
with spaces, child failures/timeouts/cleanup, skipped or absent completion
markers, invalid UCI replies, inactive workers, artifact drift, and preservation
of existing reports. Make dry runs verify all seventeen C++ test link recipes
receive target libraries and that the build-only target executes no binaries.

Each eight-check set ran the existing position/perft, NNUE, update-arithmetic,
dense-arithmetic, search, selective-policy and time-management suites, followed
by a UCI session with Hash 16 MiB and two workers. The UCI check verified
perft(3)=8,902, legal start-position best/ponder moves, completed depth 3,
readiness during infinite search, stop/quit and clean exit. Both workers
performed work; the test did not merely check that `Threads=2` was accepted.

Each runtime's NNUE checks passed twelve pinned raw/wrapped goldens,
537 incremental/full-refresh positions, 360 independent update transitions,
and 1,515 dense arithmetic cases / 84,126 repeated output comparisons. This
does **not** repeat the historical 2,057-position external SF19 stage oracle.

The additional Linux Syzygy checks used the existing, verified external
72-file / 4,381,961-byte test corpus. Both targets passed 140 exact WDL oracle
positions, DTZ root outcome/legality, special moves, clocks, fallback, malformed
files and concurrent probing. Each also passed six search scenarios with one
and four threads. These are existing three-/four-piece checks, not certification
of every table size. No table data was added to Git.

## Runtime and reproducibility

Sources started at `2029209`; this checkpoint changes build/test tooling and
documentation only. Raw evidence is local and ignored by Git under
`results/phase4e1-20261024/`: per-target `report.json` and suite logs, build logs,
`build-inventory.json`, `initial-state.json`, exact Docker commands, image/runtime
metadata and `syzygy.json`. All 24 recorded checks exited zero. Independent
saved-evidence review verified report/log consistency, binary headers/hashes,
compiler/network pins, execution labels and protected files.

Docker Engine 29.8.2 used an AArch64 LinuxKit 7.0.14 VM. The pinned
`python:3.13-slim-trixie` image supplied Python 3.13.17, Debian glibc 2.41 and
the needed target libraries. Its manifest digest was
`sha256:57b29a7c050c4e679e4bea572e14b3965cf4b5839de2da49d55e49ffc4024f39`.
ARM64 selected `linux/arm64`; x86-64 selected `linux/amd64`. The latter is
explicitly emulated evidence, even when its guest `uname` reports x86-64.

Builds used at most two compiler jobs per target. Test containers were capped
at two CPUs and 2 GiB, within the daytime allowance. Checks were short and
bounded; no puzzle campaign, match, training job or recurring schedule ran.
Named test containers were removed on completion and explicitly cleaned in the
launcher's failure path. Killing a Docker client alone is not sufficient to
clean a daemon-owned workload. Independent inspection found no Phase 4E
containers remaining; unrelated containers were left alone.

## Next checkpoint and limits

Phase 4E.2 addresses remaining target toolchain/runtime gaps, particularly
Linux RISC-V64 and Windows ARM64, plus Windows execution when available.
Network qualification/export and trainer integration follow as separately
bounded work. New CPU backends require their own arithmetic/performance proof.

This checkpoint does not establish native Linux throughput, additional playing
strength, a fresh sanitizer/race or full external stage-oracle result, custom
network compatibility, or release acceptance. No repeated puzzle audit is
needed for unchanged engine/evaluation code. The previous ProbCut timing result
remains inconclusive and its default remains off.
